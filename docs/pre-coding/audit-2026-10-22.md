## Findings

### A. README accuracy — partly accurate, restructured

Verified: the base README does not claim document authentication, regulatory
compliance, or institutional-status verification, and it does mention production
blockers. However, it compressed checklist validation, advisory OCR and the future
rules engine into single sentences, did not describe implemented OCR limits or the
synthetic nature of the fixture corpus, and did not state the complete blocker list.

Fix: README now has explicit sections for the three layers (implemented checklist
validation, implemented advisory OCR, implemented rule *governance* with no evaluator),
an explicit "not implemented / not claimed" list, the production-blocker list, and the
exact test commands. No accuracy claim is made for OCR.

### B. Rule activation governance — schema-only before this change

Verified defect. `RuleVersionDraft` enforced only effective dates and the four test
categories, and it did so exclusively through Pydantic validation. There was:

- no source-verification status, document version or retrieval/verification dates;
- no reviewer/approver identity or approval decision;
- no server-side lifecycle transition — a caller could simply set `lifecycle="active"`;
- no registry or gate that anything could consult before treating a rule as executable;
- no regression tests for reviewer identity, approval, or gate bypass.

Fix (`backend/app/rule_catalog.py`):

- `SourceProvenance` requires an exact document version and retrieval date; `status`
  may only be `verified` when `verified_by` and `verified_at` are present, and
  verification cannot precede retrieval.
- `ApprovalRecord` requires a reviewer identity, an explicit `approved`/`rejected`
  decision, a decision date and a rationale; approval cannot precede verification.
- The `ACTIVE` schema state additionally requires verified provenance, an approved
  decision, an effective date and all four test categories.
- `activation_requirements()` / `activation_blockers()` are independent, server-side
  checks that also catch objects built with `model_construct` (validators bypassed).
  They refuse caller-declared `ACTIVE` states: activation must come from the gate.
- `RuleRegistry.activate()` is the only transition to `ACTIVE`. It re-validates the
  snapshot, refuses duplicate or second active versions of the same rule ID, and the
  registry deliberately exposes no evaluate/execute method.
- **No AICTE rule is defined or active.** A regression test fails if any rule instance
  appears in `backend/app/`.

Known limit: reviewer identity is a recorded string, not an authenticated principal,
because authentication/RBAC does not exist yet. The gate is a precondition for a future
rule engine, not a deployed approval workflow.

### D. Frontend / backend / AI boundaries — PR #4 only, no fake implementations

On the audited base there is no `frontend/`, `ai/` or `WORKSTREAMS.md`; those exist
only on PR #4's docs-only head (four markdown files, no code). Inspected content is
honest: it states that neither the frontend nor the AI service is implemented, keeps
OCR in `backend/`, forbids moving OCR code without a separate reviewed integration PR,
and requires synthetic data plus human review. No change was made here to avoid
duplicating or conflicting with PR #4.

Agreed contract for later integration (unchanged, documented rather than redefined):

- OCR boundary: `backend/app/ocr_adapter.py` (`OCRField`, `OCRDocumentResult`,
  `parse_iso_date_candidate`) — engine-neutral, no engine dependency.
- Pipeline boundary: `process_institution_document(image_bytes, engine)` returns
  advisory fields only, always with `requires_human_review=True`.
- API boundary: `POST /api/v1/validate` returns
  `validation_scope="caller_supplied_checklist_only"`; no document uploads.
- Rule boundary: only `RuleRegistry`-activated versions may ever reach an evaluator;
  the evaluator does not exist yet.
- Any move of OCR code into `ai/` needs its own PR with import, test, dependency and
  packaging review.

### E. OCR robustness — five defects reproduced and fixed

Reproduced defects on the base commit:

1. **Reversed, equal and multi-year academic years were accepted**:
   `2027-2026`, `2026-2026` and `2026-2030` were all extracted as values.
2. **Non-finite engine confidence was silently rewritten**: a `NaN` Tesseract
   confidence became `1.0` (maximum) because `min(1.0, nan)` returns `1.0`;
   `inf` and `5.0` were also clamped to `1.0`; `-0.5` words were dropped silently.
3. **`extract_institution_fields` clamped any confidence** (including `NaN`, `inf`
   and `2.0`) to a valid-looking `1.0` instead of rejecting it.
4. **Malformed engine output crashed with `AttributeError`**: non-string word text
   (`'int' object has no attribute 'strip'`) and non-`OCRRawResult` return values.
5. **No aggregate output bound**: a 200,000-word engine result was processed without
   limit; only per-call behaviour was bounded.

Also verified: `_validate_image_bytes` is structural (`Image.verify()` does not fully
decode JPEG), so a truncated JPEG passed validation and later failed inside the engine
as a generic `RuntimeError`.

Fixes (`backend/app/ocr_pipeline.py`):

- `OCRWord` validates text type, finite confidence in `[0.0, 1.0]` and positive
  page/line integers; invalid engine values are rejected, never rescaled.
- `OCRRawResult` requires a non-empty engine name and coerces word/warning sequences.
- The Tesseract adapter drops non-finite, negative and unparsable confidences, and now
  separates decode failures (`OCRInputError`) from engine failures (`RuntimeError`).
- `process_institution_document` rejects non-`OCRRawResult` results and enforces a
  100,000-character aggregate OCR text budget before grouping.
- `extract_institution_fields` rejects non-string text and out-of-range or non-finite
  confidence, bounds input text length, and accepts an academic year only when the end
  year is exactly `start + 1` (reversed, equal and multi-year spans stay unresolved).
- A contradictory issue/valid-until pair now produces an explicit warning instead of a
  silent, apparently consistent result.

Regression tests were added for every item above (synthetic only). The fixture corpus
remains a 10-case regression set; it is **not** a labelled held-out benchmark, and no
OCR accuracy figure is claimed.

### F. Security and production readiness — claims verified as blockers

Verified by inspection: there is no authentication, authorization/RBAC, tenant
isolation, private storage, malware scanning, durable audit, retention/deletion
control, or official-source rule approval. The only routes are `/health` and
`/api/v1/validate` (no file-upload route). The README and the pre-coding documents keep
production use blocked. No control was simulated, mocked into existence, or claimed.

One documentation correction: `docs/pre-coding/implementation-status-2026-10-23.md`
cited Actions run #56 as its "latest code-inclusive evidence", but that run executed on
head `f160abc`, not the branch head `014403a`. The status document now records the
correction and the run that actually covers `014403a`.

## Remaining risks and blockers

1. No authenticated principal backs the approval/reviewer identities; RBAC, tenant
   isolation and durable audit are still missing.
2. No rule evaluator exists, and no AICTE rule is verified for applicability or
   amendments; Phase 0 gates stay open.
3. No labelled, held-out English/Hindi OCR corpus; accuracy is unmeasured
   (multi-frame TIFF, PDFs and bounding boxes are also unimplemented).
4. Real Tesseract execution could not be re-verified in this sandbox (the system package
   is unavailable); the optional CI job is the evidence for that path.
5. Frontend and AI workstreams remain documentation-only (PR #4).
